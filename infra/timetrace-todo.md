# TimeTrace 改进建议与目标

> 本文只记录待实现或待验证的工程计划，不是已完成事实，不直接粘贴进简历。每项完成后需补代码、测试、真实环境数据与诚实边界，再迁入 [timetrace.md](timetrace.md)。

## P0：先修正可测量性与现有可靠性细节

### 1. 建立同条件上传基准

目标：把“路径差异”“吞吐优化”“带宽节省”拆成可比较的三组数据。

- 固定同一批 outbox 条目、图片大小分布、endpoint、并发度与机器环境。
- 分别记录串行与并发发送的：队列项/秒、活动记录/秒、MB/s、请求延迟 P50/P95、重试次数、失败类型。
- 单独记录 LAN、公网 HTTPS、SSH 隧道三条路径，不跨路径组成 before/after 箭头。
- 对上传条目明确分类：record-only、screenshot、close；避免“条/秒”口径含糊。
- 验证服务端记录数、截图数、幂等命中数与客户端 ack 数，分别说明元数据和图片的完整性。

验收：生成一份可重复执行的 benchmark 脚本和 Markdown 报告，所有简历数字能够从报告直接定位。

### 2. 修复并发 token bucket 的额度预留

现状风险：多个并发协程在额度不足时会同时 sleep，等待前没有原子预留 token，恢复后可能一起放行并突破 `max_kbps`。

- 用 `asyncio.Lock` 保护 refill 与 reserve，或改为单独的带宽调度协程。
- 等待前先计算并占用未来额度，禁止多个 waiter 使用同一批 token。
- 增加 fake clock 测试，覆盖 `concurrency > 1`、单条大于一秒预算、停止事件和连续小包。
- 基准验证长期平均速率与短时 burst 均符合配置容差。

验收：并发 1/2/4/8 下的总发送速率均落在目标带宽允许误差内。

### 3. 区分可重试失败与永久失败

- 连接超时、5xx、endpoint 不可用进入指数退避与路径重选。
- 鉴权失败、请求格式错误、blob 损坏等永久失败进入 quarantine / dead-letter，不无限堵住队首。
- dead-letter 保存 entry id、失败类型、最后响应与本地 blob 路径，提供 CLI 查看和人工重放。
- 超大历史图片进入隔离队列，保留活动元数据并明确图片状态，不直接与普通小图竞争 FIFO。

验收：构造一个永久失败项时，后续无依赖记录仍可继续同步；隔离项可定位、修复并重新入队。

## P1：面向弱网的自适应同步

### 1. 元数据、缩略图、原图分级上传

目标：只有一条低质量公网路径时，优先保证活动时间线及时可用。

- 将同一次采集拆为三个优先级：活动元数据 > 缩略图 > 原图。
- 弱网或积压较高时先上传元数据和缩略图，原图保留在客户端低优先级队列。
- 网络恢复或切回 LAN 后自动补传原图，服务端以内容 hash 关联并升级图片状态。
- UI 明确显示 metadata-only、thumbnail-ready、full-ready 状态，避免把暂缺原图误判为处理失败。

验收：模拟低带宽与断网时，新增活动能在限定时间内出现在时间轴；恢复 LAN 后原图自动补齐。

### 2. 自适应图片规格

- 依据近期有效吞吐、RTT、积压字节数和失败率划分 normal / constrained / recovery 状态。
- constrained 状态生成较低分辨率或质量的上传副本，本地保留原始 JPEG，后续可补传高质量版本。
- 设置滞回阈值，防止网络临界值附近频繁切换质量档位。
- 记录每种档位的字节数、VLM 描述质量和文字可读性。

验收：在统一活动回放集上给出字节节省比例、VLM 字段一致率与关键文字漏读率。

### 3. 端侧画面变化检测

- 复用现有 SHA-256 与 pHash：完全相同画面直接复用 blob，近似静止画面降低截图频率。
- 窗口标题、进程、URL 或活动窗口变化时强制采集；长时间静止仍周期保留关键帧。
- 为小范围文字更新保留保护策略，避免单纯 pHash 阈值漏掉终端输出、数字和聊天内容变化。
- 通过历史截图回放标注“应采/可跳过”，调节汉明距离阈值和强制关键帧周期。

验收：报告平均每日图片数、上传字节数、可跳过比例和重要变化漏检率。

### 4. 内容寻址 blob 与跨记录去重

- 以编码后图片 SHA-256 作为 blob key，记录与 blob 建立引用关系。
- 客户端先提交 manifest，服务端返回缺失 hash，仅上传不存在的图片。
- blob 引用计数或可达性扫描负责回收，删除单条活动不立即误删共享文件。
- 幂等从 `(record_id, sha256)` 扩展为“全局 blob 唯一 + 记录引用唯一”。

验收：重复截图只保存和上传一份；并发提交同一 hash 不产生重复文件或孤儿引用。

### 5. 大 blob 断点续传

- 元数据与 blob 分离，blob 使用分片编号、总长度与整文件 hash。
- 服务端查询已接收分片，客户端只重传缺失部分；完成后校验整文件 hash 再原子发布。
- 对小图片保留单请求快路径，避免为常规 0.5MB JPEG 引入额外 RTT。

验收：上传大图中途断网后只补传剩余分片；最终文件 hash 与客户端一致。

## P1：完成分层 Agent 主线

### 1. 统一工具真源

- 以 `agent/tools.py` 中的 schema 与 dispatch registry 作为唯一工具定义。
- 内置 Agent、MCP、ReportGenerator 和工具说明从同一 registry 注册或生成。
- 将 `query_stats` 暴露给 MCP，明确 `ask_agent` 的保留价值或移除路径，消除手写工具清单漂移。
- 增加一致性测试：MCP 工具集合、内部 Agent schema 和文档必须覆盖同一 registry。

验收：新增或删除一个工具时只修改一个注册源，其余入口测试自动发现漂移。

### 2. 落实由粗到细的查询策略

Agent 按以下成本顺序选择工具：

1. 精确时长、次数、应用或分类问题先用纯 SQL `query_stats`。
2. 总结某天或某周先读 day/week 摘要。
3. 根据相关窗口向 6h、1h、5min 摘要下钻。
4. 搜索具体事件使用摘要或语义检索。
5. 摘要证据不足时才读取窄时间窗的原始活动记录。

- 更新默认 system prompt 和工具描述，使上述顺序成为明确策略。
- 为单次工具输出、总迭代次数和会话上下文设置预算。
- 工具结果返回推荐的下一层 grain 和可继续下钻的时间范围。

验收：在固定问题集上，统计工具选择正确率、平均调用次数、读取原始帧比例与总 token。

### 3. 摘要语义检索

- 为 `summaries` 建立 FTS 与 embedding 双通道检索，而不是在已取出的窗口中仅做子串过滤。
- 结果按 grain、时间范围与相似度返回，并支持从命中摘要继续下钻。
- 使用 RRF 融合关键词与语义通道，保留各通道得分和命中原因。

验收：对“什么时候处理过某类问题”等历史问题建立标注集，报告 Recall@K 与时间窗命中率。

### 4. 回答证据、覆盖范围与水位

- 每个工具结果返回数据时间范围、粒度、是否截断、摘要生成状态和最新处理水位。
- Agent 最终回答附可点击的时间窗或活动记录引用，便于回到时间轴查证。
- 部分覆盖时明确已覆盖区间和待处理尾部，不把局部数据表述为完整统计。

验收：所有涉及数字和历史事件的回答均可定位到摘要窗口或原始记录。

### 5. 建立 Agent 评测集

- 收集真实使用问题，覆盖统计、时间概览、具体事件检索、跨日总结、分类修改和数据不足六类。
- 标注正确时间范围、预期工具路径、关键事实与允许的回答边界。
- 指标至少包含：事实正确率、时间范围正确率、工具选择正确率、引用可追溯率、平均工具调用数、平均 token。
- 在模型、prompt、工具 schema 或摘要策略变化后自动回归。

验收：形成版本化数据集与可重复评测报告，简历中的 Agent 表述有真实问答证据支撑。

## P2：产品化与长期运行

### 1. 自动磁盘配额

- 分开统计原图、缩略图、outbox 与数据库占用。
- 支持按总容量、保留天数和数据优先级回收。
- 回收前维护数据库引用和 blob 可达性，保留摘要与活动元数据。

### 2. OCR 与隐私处理

- 在上传或送入模型前识别密码框、令牌、卡号与指定区域，并按配置遮挡。
- OCR 文本作为独立可搜索字段，保留来源截图和时间范围。
- 对误遮挡与漏遮挡建立小规模评测集。

### 3. 向量索引升级

- 数据规模达到阈值后，将 NumPy 全表余弦扫描替换为可持久化 ANN 索引。
- 保留小数据量下的精确扫描路径，通过基准决定切换阈值。

### 4. 资源与稳定性基准

- 持续记录客户端 CPU、内存、磁盘写入、每日图片量和服务端 VLM 队列延迟。
- 覆盖单机模式、Home Lab 模式、断网恢复与长时间积压四类场景。
- 输出 P50/P95 与资源峰值，不只记录平均值。

### 5. 安装与升级

- 提供 Windows 安装包、首次启动配置与升级迁移流程。
- 保证单机模式无需手工启动多个服务；Home Lab 模式提供可验证的客户端/服务端引导。

## 建议实施顺序

1. 同条件 benchmark，先把所有性能口径测准。
2. 修复 token bucket，并加入永久失败隔离。
3. 统一 Agent/MCP 工具真源，完成由粗到细的默认查询策略。
4. 实现元数据/缩略图/原图分级上传和弱网恢复补传。
5. 实现端侧变化检测，再用真实回放数据调阈值。
6. 依据去重命中率决定是否继续做内容寻址和断点续传。
7. 建立 Agent 评测集与回答证据链。
8. 再推进磁盘配额、OCR、ANN、资源基准和安装包。
